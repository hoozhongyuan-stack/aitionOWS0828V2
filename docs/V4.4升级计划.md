## 二、批量操作详设

### 2.1 统一交互

```
☐ │ 标题        │ 栏目   │ 状态   │ 操作
☑ │ 文章 A      │ 新闻   │ 草稿   │ …
☑ │ 文章 B      │ 教程   │ 已发布 │ …
────────────────────────────────────────────────
已选 2 项   [批量发布] [批量下架] [批量删除]  取消选择
```

- **表头 checkbox** = 全选本页（不跨页，避免误伤）；有选中时表头显示"部分选中"态（indeterminate）
- **操作栏**在选中 > 0 时出现，位置固定在列表上方（不随滚动丢失）
- **切换筛选/翻页时清空选择**（避免"选中了看不见的项"的误操作）
- 每个批量操作按钮**带条数**（"批量删除（3）"）

### 2.2 各页面的动作与权限

| 页面 | 路由 | 批量动作 | 权限守卫 |
|---|---|---|---|
| 内容 | `/admin/content` | 发布 / 下架 / 转草稿 / 删除 | `requirePerm("content")` |
| 栏目 | `/admin/categories` | 显示 / 隐藏 / 删除 | `requirePerm("content")` |
| 导航 | `/admin/navigation` | 显示 / 隐藏 / 删除 | `requirePerm("content")` |
| 注册用户 | `/admin/users` | 启用 / 禁用（**不含删除**） | `requireOwner()` |
| 互动审核·评论 | `/admin/ugc`（评论 Tab） | 通过 / 驳回 / 删除 | `requirePerm("moderation")` |
| 互动审核·投稿 | `/admin/ugc`（投稿 Tab） | 通过 / 驳回 / 删除 | `requirePerm("moderation")` |

**业务规则逐项执行**（不做"全成功或全失败"）：
- 栏目：**含子栏目或含内容**的项**跳过**并回报原因（沿用现有单个删除的规则）
- 用户：跳过**主账号**与**不存在/已删除**的 id
- 内容：跳过**不存在**的 id

### 2.3 安全护栏（本项设计重点）

| 护栏 | 做法 |
|---|---|
| 单次上限 | **100 条**（超出直接拒绝并提示分批） |
| 删除类二次确认 | 弹窗文案带条数："确认删除选中的 3 项？此操作不可恢复" |
| **注册用户不开放批量删除** | 注册用户连带数据多（订单/评论/收藏/投稿），误删影响大——只给批量启用/禁用，删除保持单个二次确认 |
| 逐项结果回执 | 返回 `{ ok: [id...], skipped: [{id, reason}...] }`，前端 toast 汇总（"成功 3 项，跳过 1 项（栏目非空）"） |
| 审计 | 一次批量操作写**一条** admin-log：`action: "content.batch.delete"`, `detail: "ids=1,2,3"`（截断保护沿用 logAdmin 的 slice） |
| 权限不放宽 | 批量端点用与单个操作**完全相同**的守卫，不因"批量"降级校验 |

### 2.4 实现要点

**后端**（每资源一个端点，共 6 个）：
```
src/app/api/admin/contents/batch/route.ts
src/app/api/admin/categories/batch/route.ts
src/app/api/admin/nav/batch/route.ts
src/app/api/admin/users/batch/route.ts
src/app/api/admin/ugc/comments/batch/route.ts
src/app/api/admin/ugc/submissions/batch/route.ts
```
统一形态：`POST { ids: number[], action: "publish"|"offline"|"draft"|"show"|"hide"|"delete"|"enable"|"disable"|"approve"|"reject", payload?: {} }`

**服务层**：在各自 `src/server/**` 加 `*Batch(input)` 函数，内部循环调用既有单条逻辑（**复用而非另写**，保证规则一致：如栏目删除的"非空禁删"、内容删除的关联清理）

**前端公共件**（避免 5 处重复）：
```
src/components/admin/use-batch-selection.ts   # 选中状态、全选/反选/清空
src/components/admin/batch-action-bar.tsx     # 已选计数 + 动作按钮 + 取消
```

### 2.5 验收

## 三、商品管理列表视图（方案 B）

**现状**：`grid gap-4 sm:grid-cols-2 lg:grid-cols-3` —— 一排 3 个，一屏可见约 3–6 个。

**改法**：在筛选栏右侧加**视图切换**（网格 / 列表），**默认视图 = 列表**（用户确认），偏好存 `localStorage`。

**列表视图列设计**：

| 列 | 内容 | 宽度 |
|---|---|---|
| 缩略图 | 封面或图集首图，40×40 圆角 | 56px |
| 名称 | 标题（截断，hover 显示全称） | 自适应 |
| 栏目 | 栏目名 | 120px |
| 价格 | 有价显示币种+金额；无价显示"仅询盘"标签 | 110px |
| SPU | 货号（无则 `—`） | 120px |
| 状态 | 草稿/已发布/已下架（沿用 Badge） | 90px |
| 更新时间 | 相对时间或日期 | 110px |
| 操作 | 编辑（复用现有入口） | 80px |

**一屏可见 15–20 条**（比现在提升 3–5 倍）。

**实现要点**：
- 纯前端：`products/page.tsx` 加 `viewMode` state + 两套渲染分支
- 复用现有筛选/搜索/分页逻辑，**不改任何 API**
- 网格视图保持现状（不破坏用户习惯），切换是增强而非替换

**验收**：

- [ ] 列表视图一屏 ≥15 条；缩略图、价格（含"仅询盘"）、SPU、状态正确

## 四、前台透明感

**目标**：前台卡片/面板具备可调的通透度（毛玻璃质感），**默认值与现状一致**（不做任何调整的站点观感零变化）。

### 4.1 配置项（后台「主题外观」新增）

| 配置 | 形态 | 默认 | 说明 |
|---|---|---|---|
| 卡片通透度 | 滑杆 0.60–1.00 | **1.00** | 1.00 = 完全不透明（现状）；越低越透 |
| 背景模糊 | 开关 | **关** | 开启后卡片 `backdrop-filter: blur()`（真正的毛玻璃） |
| 页头通透 | 开关 | **关** | 开启后页头半透明 + 模糊，滚动时内容从底下透出 |

**关键约束**：
- 通透度 **不低于 0.60**（低于此对比度无法保证可读性，UI 层直接限制）
- 与 `prefers-reduced-transparency` / `prefers-reduced-motion` 联动降级

### 4.2 实现要点

- **主题配置结构扩展**：`ThemeConfig` 加 `cardAlpha?: number`、`cardBlur?: boolean`、`headerGlass?: boolean`（**全部可选**，缺省 = 现状 → 存量站点零变化）
- **CSS 变量**：新增 `--surface-alpha`、`--surface-blur`，由根布局注入（沿用 `buildThemeCss` 管线）
- **落点**：卡片（`.bg-card`/`[data-slot="card"]`）、前台页头、必要时面板；**不动后台**
- **各主题适配**：四个主题段的卡片规则改为引用变量（极光原本就是毛玻璃，默认值调好后其观感保持）
- **性能**：`backdrop-filter` 只在开关开启时生效；移动端默认关闭模糊（可后续放开）

**验收**：
- [ ] 后台可调通透度与模糊开关，**保存即生效**
- [ ] 默认值下四主题观感与升级前**完全一致**（零回归）
- [ ] 通透度 0.6 时文字对比度仍达 WCAG AA（正文 ≥4.5:1）
- [ ] 开启模糊后滚动流畅（移动端不卡顿）；`prefers-reduced-transparency` 下自动关闭
- [ ] Safari 正常（`-webkit-backdrop-filter`）

## 五、版本信息展示（后台）

**需求**：后台登录页与后台内部需展示系统版本号与更新时间，且**随版本更新自动变动**。

**展示位置**：

| 位置 | 内容 | 用意 |
|---|---|---|
| **后台登录页**底部 | `爱神AiTion v4.4.0 · 构建于 2026-09-11 14:30` | 未登录即可见——排查问题时第一眼确认"生产到底跑的是哪个版本" |
| **后台侧边栏**底部 | `v4.4.0`（hover 显示完整构建时间） | 日常可见、不打扰 |

**技术方案（自动变动，零人工维护）**：
- `next.config.ts` 构建时注入两个值：
  - `NEXT_PUBLIC_APP_VERSION` ← 读 `package.json` 的 `version`（发版流程本就有"改版本号"这一步，天然同步）
  - `NEXT_PUBLIC_BUILD_TIME` ← 构建时刻的 ISO 时间戳（每次 `docker build` 自动更新）
- 显示格式：`v4.4.0 · 构建于 2026-09-11 14:30`（按**北京时间**格式化，不受访问者本地时区影响）

**为何用"构建时间"而非"发布日期"**：发布日期要人工维护、容易忘；构建时间自动且语义更准——它等于**这个包是什么时候部署上线的**，排障时"生产跑的到底是几点的包"一目了然。

**说明**：`NEXT_PUBLIC_*` 会内联进客户端 JS，即版本号对访问者可见。对本系统无安全影响（版本号本身不是秘密），而这正是本需求的目的（让人看到版本）。

**验收**：
- [ ] 登录页底部显示版本号与构建时间
- [ ] 后台侧边栏底部显示版本号（hover 可见完整时间）
- [ ] 改动 `package.json` 版本号并重新构建后，显示随之变化
- [ ] 仅重新构建（不改版本号）时，构建时间更新
- [ ] 时间按北京时间显示、格式统一

## 六、后台主题解耦（用户明确要求）

**问题**：`data-theme` 目前挂在 `<html>` 上（`src/app/layout.tsx:29`），因此**后台也被主题 CSS 段命中**——选窖藏后台按钮变红、选禾野变绿，管理界面观感随前台漂移，且深色主题下后台可读性下降。

### 5.1 技术路径（建议：把 data-theme 移出 html）

**方案 X（推荐）**：`data-theme` 从 `<html>` 移到**前台布局容器**，后台天然不受影响。

改动：
1. `src/app/layout.tsx`：`<html>` 去掉 `data-theme`（保留 `lang`）
2. `src/app/[locale]/(site)/layout.tsx`：根容器 div 加 `data-theme={theme.preset}`
3. **逐条调整四个主题段的 CSS**：把依赖 html/body 层级的写法改为作用于容器本身
   - 例：`[data-theme="aurora"] body { background: ... }` → `[data-theme="aurora"] { background: ... }`
   - 涉及 aurora / harvest / cellar 三段（classic 无段），约 40–60 条选择器需要审查
4. 根级 404（不在前台布局下）：保留 `:root` 注入的色彩变量即可（无主题段特效，可接受）；或单独挂载主题容器

**方案 Y（备选，不推荐）**：保留 html 上的 data-theme，后台容器加高特异性重置（`html body [data-admin] …` + 覆盖各主题的卡片/按钮/标题规则）——需要为 4 个主题逐条写覆盖，规则多、易漏、今后每加主题都要补，**维护成本高**。

**为何推荐 X**：一次到位，之后新增主题无需考虑后台；后台与前台彻底解耦，语义清晰。

### 5.2 后台统一中性配色的落点

- 后台容器（`(admin)` 布局）显式声明中性基调，不依赖主题变量：
  - 变量层：后台作用域内重置 `--primary`/`--secondary`/`--border`/`--radius` 等为 shadcn 默认
  - 效果层：不加载任何主题段（X 方案下天然满足）
- **后台不参与透明感**（第四节明确只做前台）

**验收**：
- [ ] 依次切换 经典/极光/禾野/窖藏，**后台外观完全不变**（截图比对四主题下的同一后台页面）
- [ ] 前台四主题效果与升级前**逐像素一致**（X 方案改造的最大风险点，需逐主题比对）
- [ ] 根级 404 页面正常（色彩正确、无样式缺失）
- [ ] 后台在四主题下都可读（对比度达标）

## 九、风险与回滚

| 风险 | 影响 | 对策 |

## 附：阶段 1 实施记录（2026-09-11）

**计划里的"方案 X / 方案 Y 二选一"在实施中被修正为"两者必须结合"** —— 这是本阶段的关键发现：

- **方案 X（把 data-theme 移出 `<html>`）**：解决的是"主题**样式段**"（卡片毛玻璃、光晕、标题渐变、卡片圆角等）—— 已实施 ✓
- **方案 Y（后台 `[data-admin]` 高特异性重置）**：解决的是"主题**颜色变量**"—— 变量由根布局按 `:root` 注入，**全站生效且与 data-theme 无关**，移属性解决不了

**只做 X 的实测结果**：后台不再有主题特殊样式，但底色仍是墨黑、按钮仍是朱砂红（变量仍在起作用）。所以两者缺一不可。

**实施中另发现两个坑（均已修）**：
1. 后台容器用 `bg-muted/30`（半透明），会透出 body 的主题底色（深色主题下是墨黑）→ `[data-admin]` 必须自带不透明 `background-color`
2. 只重置 CSS 变量不够 —— 标题等元素靠**继承 body 的 `color`** 取色，而 body 的 color 来自主题，会一路继承进来 → `[data-admin]` 必须显式设 `color: hsl(var(--foreground))`

**验收实测**：在窖藏（深色墨金）与禾野（浅色暖绿）两个反差主题下，后台计算样式**完全一致**（`background: rgb(255,255,255)` / `color: rgb(2,8,23)` / `--primary: 222.2 47.4% 11.2%` / `--radius: 0.5rem`）；前台四主题效果**与升级前一致**（窖藏容器的背景渐变/光晕/衬线标题均保留）。
