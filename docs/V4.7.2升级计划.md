## 一、问题确认(证据)

### 1. 分页器展示与实际不符 —— 接口漏读 `pageSize`(全后台仅此一页)

**根因**:内容管理页请求带了 `pageSize`,但 `GET /api/admin/contents` **没有读取该参数**(只读 page/categoryId/status/source/keyword/dateFrom/dateTo),服务层于是用默认值 **20**。

登录态实测(本地,直接打接口):

```
请求 pageSize=10 → 接口声明 pageSize=20     ← 参数被忽略
请求 pageSize=20 → 接口声明 pageSize=20
请求 pageSize=50 → 接口声明 pageSize=20     ← 「每页」下拉从未生效
对照·商品接口   → pageSize=10 声明 10、pageSize=50 声明 50  ✅ 正常
```

**三条连锁后果**(与用户截图完全对应):页面实际拉 20 条而顶部写「每页 10 条」;旧式分页器用接口返回的 `data.pageSize=20` 算 → 23 条内容显示 **「1 / 2」**;共享分页器用界面的 `pageSize=10` 算 → **「第 1 / 3 页」**。

**全后台排查**:8 个带分页的列表页(内容/商品/订单/注册用户/互动审核/操作日志/文件/访问明细)中,只有**内容页**存在参数漏传;**且内容页是全后台唯一同时挂了两套分页器的页面**(遗留的「上一页/下一页」+ V4.0.2 的共享分页器)。其余 7 页的接口均正确读取 `pageSize`。

同类风险提示:这是"UI 发了、接口不认"的**第三次**(前两次:媒体 `folderId/keyword`、内容 `price/spu` 字段静默剥离),建议本次补一条回归测试锁住。

### 2. GEO 监测页数字没对齐 —— 子表缺表头,两张表各自计算列宽

AI 渠道引荐主表有完整 `<thead>`(渠道/落地页/点击/访客),而下方**「搜索引擎引荐」子表没有 `<thead>`**,只有数据行。两表都是 `w-full` 自动列宽 → 列宽各算各的,**点击/访客两列上下对不齐**(截图中 "Google 搜索" 行的 `/zh-CN` 被推到右侧即是此现象)。

**全站从未使用过等宽数字**(`tabular-nums` 检索结果为空),数字列虽然 `text-right` 但数字宽度不一,看起来依然参差。

**排查其他页**:访问明细页的两张表都有表头且结构一致 ✅;GEO 监测页「被爬 Top10」表也有表头 ✅ → **数字对齐问题只此一处**。

### 3. 豆包有记录、DeepSeek 无 —— 机制正常,但缺少"能看到真相"的诊断

**生产实测**:

| 项 | 数据 |
|---|---|
| 豆包引荐 | **2 次点击**(09-14 21:38、09-15 09:20),落地页 `/zh-CN/article/post-mtyhb49w` ✅ |
| DeepSeek 引荐 | **0 条**(引荐表仅豆包 + Google 搜索) |
| 抓取侧 | 只有 ClaudeBot / GoogleOther / 疑似 curl,**无任何 deepseek 相关 UA** |
| 豆包点击前后 ±15 分钟 | 无抓取事件(说明豆包是"用户点击"渠道,不是爬虫) |

**DeepSeek 无记录的三种可能**:① 客户端(App/桌面)内嵌浏览器**不发送 Referer**;② 网页版引用链接带 `rel="noopener noreferrer"`,浏览器**不发 Referer**;③ 从回答里**复制粘贴**打开(同样无 Referer)。

**当前无法区分的原因**:白名单机制是"Referer 命中才记录",**未命中的 Referer 一律不落库**(当初为隐私与噪声考虑)→ 于是"没带 Referer"与"带了但没收录"在数据上不可区分。这样每次都要靠猜。DeepSeek 根域已在 V4.7.0 补进白名单,所以"网页版直接点击"一定能记上。

**附带发现(口径瑕疵)**:`recordReferral(..., isNewVisitor = true, ...)` **恒为 true** → 引荐表的「访客」列实际等于「点击」列,没有去重语义(截图 `点击 2 / 访客 2` 即此)。容易让人误读为"2 个不同访客"。

### 4. 前台没有全站搜索(但栏目内搜索已存在,复用成本低)

现状:栏目页/商品筛选栏**已有关键词搜索**(`?q=` → 服务层 `translations.title/summary contains`,URL 驱动、服务端过滤);但**没有全站搜索入口**——页头无搜索框,也没有 `/search` 路由。

## 二、修改方案

### A. 分页器修复(0.25 天)

1. `GET /api/admin/contents` 补上 `pageSize` 透传(与其余 6 个列表接口同口径)
2. 服务层 `listAdminContents` 的钳制补下界:`Math.min(100, Math.max(1, q.pageSize ?? 20))`(现在只有上界,传 0 会取 0 条)
3. **删除内容页遗留的旧式分页器**(`上一页/下一页` 那段,以及只服务于它的 `totalPages` 变量)—— 全后台统一只保留共享分页器
4. 回归测试:断言「接口声明的 `pageSize` === 请求值」,并覆盖 `page`/`categoryId`/`status`/`keyword` 等既有参数(locks the class of bug,不是只修这一处)

### B. GEO 数字对齐(0.25 天)

1. **合并两张引荐表为一张**:同一个 `<table>`,一个 `<thead>`(渠道/落地页/点击/访客),用一行小标题分隔「AI 渠道引荐」与「搜索引擎引荐(单独口径)」→ 列宽天然一致,不会再出现上下错位
   - 备选(更小改动):保留两张表,给搜索引擎那张补上同样的 `<thead>`;但两张表的数据行构成不同(一个有表头一个没有)仍可能因内容宽度差异错位,**推荐合并**
2. 所有数字单元格统一加 `tabular-nums`(等宽数字):引荐表 点击/访客、Top10 次数;表头同步右对齐
3. 落地页列给固定宽度 + `truncate` + `title`,避免长路径把列宽带偏

### C. 引荐来源可观测性诊断(0.75 天)

**目标**:下次你从 DeepSeek 点进来时,后台能直接告诉你"它到底带了什么 Referer"或"它压根没带"。

**做法(免迁移,复用现有 `kind` 字符串列)**:

1. 采集端(`app/[locale]/layout.tsx`):当 `referer` **存在**、但**未命中任何白名单**(AI 与搜索)、且**不是本站域名**时,记录一条 `kind = "unknown"` 的引荐 —— `source` 只存 **Referer 的主机名**(如 `chat.deepseek.com`),**不存完整 URL**(隐私),落地页存 path
2. 配额与去噪:沿用「疑似抓取」的日采样上限思路(默认 200 条/天),超限只累加计数;空 Referer 不记录(技术上无从记录)
3. 展示:
   - **访问明细页**新增第 5 个分区「未识别来源」(复用现有 Tab/筛选/CSV 导出)
   - **GEO 监测页**在引荐卡片下加一行小字「未识别来源 Top5」+ 明确标注「**仅供参考,不等于 AI 渠道**(可能是普通外链)」
4. 口径隔离:确保 `unknown` 不进入 AI / 传统搜索 / 疑似抓取三个分区的任何统计与导出(现有查询均按 `kind` 精确过滤,只需补上疑似分区的采样上限判断)
5. 交付后自测:在 DeepSeek 网页版回答里**直接点**链接 → 若出现「未识别来源:chat.deepseek.com」说明它带了 Referer 但格式与白名单不符;若连这条都没有,则确证它**未发送 Referer**(客户端/`noreferrer`),那就是对方行为,服务端无法补记

**可选(需你定)**:同时修「访客」口径 —— 要么改成按「来源 + 日期」去重(同一天同一来源只计 1 个访客),要么把列名改为「到达次数」以避免误读。

### D. 前台全站搜索(推荐档,1 天)

**入口**
- 页头右侧加搜索图标(桌面点击展开输入;移动端全屏输入),提交后进入结果页
- 结果页 `/[locale]/search?q=&type=&page=`,服务端渲染(与现有"URL 驱动、服务端过滤"的风格一致,链接可分享)

**数据与逻辑**
- 新增服务层 `searchPublished(locale, q, { type, page, pageSize, kind })`:范围 = **可见栏目下的已发布内容**,匹配**标题 + 摘要 + 栏目名**;`type` 支持 全部 / 文章 / 商品
- **暂不搜正文**:正文是大字段,`LIKE '%x%'` 无法走索引,当前数据量没问题、将来是性能坑(上百篇以上再评估 SQLite FTS5,中文需 trigram/jieba 分词,成本高)
- 排序:**标题命中优先**,其次发布时间倒序(比纯时间倒序有用得多);实现上先取匹配集(上限 200)再在服务端排序,并在代码注释里标明规模上限

**推荐档的三项体验**
1. **类型分组**:结果页按「文章 / 商品」分组展示(或 Tab 切换),各自显示条数
2. **命中高亮**:命中词在标题/摘要里高亮 —— 用 React 切片渲染,**不使用 `dangerouslySetInnerHTML`**(不再开 XSS 面)
3. **热门关键词兜底**:无结果或首次进入时展示热门关键词 chip,热度按**文章 `seoKeywords` 聚合**统计(正好复用 V4.7.0 新增的关键词字段)

**顺带(1 行改动,建议一起做)**:文章详情页页尾的关键词 chip 变为可点击 → 跳 `/search?q=<关键词>`。这让 V4.7.0 做的关键词从"纯展示"变成"可探索",也让搜索有自然入口。

**SEO/GEO**
- 结果页设 `noindex, follow`(搜索结果是薄内容,不值得收录);站内搜索**不能替代 GEO**(AI 答题不经过站内搜索,这一点已在 V4.7.0 前的核查中确认)
- 站内搜索结果页不写入 sitemap

**i18n**:新增 `search` 命名空间(中英同步):占位符、结果数、空态、类型标签等

**测试**:服务层单测(标题命中/摘要命中/排除非 PUBLISHED/排除不可见栏目/type 过滤/标题命中排序优先/空查询)+ SSR 集成断言(结果页含命中项与高亮标记、`noindex`)+ 热门关键词聚合

## 三、验证要点

1. **A**:内容页「每页」切 10/50/100 → 实际返回条数、分页器页数、顶部文案三者一致;页面上只存在一个分页器;其他 7 个列表页回归无变化
2. **B**:引荐表两段数据的点击/访客列在**同一 x 坐标**上;数字等宽对齐;长落地页路径截断且悬浮可见全文;浅色/深色两种外观正常
3. **C**:从 DeepSeek 网页版点链接后,「未识别来源」出现对应主机名(或确证未发送 Referer);AI/传统搜索/疑似三个分区的统计与 CSV 导出不受污染;`unknown` 采样上限生效;只存主机名(不含完整 URL 与查询串)
4. **D**:搜中文词能命中标题与摘要;类型切换正确;高亮不破坏 HTML;无结果时显示热门关键词;移动端输入体验正常;结果页 `noindex`;关键词 chip 点击跳搜索
5. **回归**:文章详情页/栏目页/首页渲染与 OG、JSON-LD 不受影响
6. **门禁**:`tsc --noEmit`、`lint`、`vitest run`(现有 254 用例)、`next build`
