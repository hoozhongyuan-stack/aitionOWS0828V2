> 状态:**已确认并开发完成**(2026-09-20,用户采纳全部推荐选项 A1/B1/C1/D1/E1)
> 目标版本:与 V4.8.0(拟真数据 + 收藏)**合并发布为 V4.8.0**

## 1. 需求理解

后台能把某篇内容「置顶」,让它在前台列表里顶在最前面,不被新内容挤下去。典型场景:

- 常青内容(如「服务与合作方式」)长期挂在栏目页前列;
- 活动/专题文章在一段时间内(如两周)保持曝光,到期自动下来;
- 多条置顶时,按运营意图控制先后。

## 2. 生效范围(明确边界,不多不少)

| 前台出口 | 是否生效 | 依据 |
|---|---|---|
| 栏目页列表 | **是** | `listPublishedByCategory`(src/server/content/index.ts:596-604,栏目页与首页楼层共用同一函数) |
| 首页「最新动态」 | **是** | `listLatestPublished`(index.ts:749,`take=6`) |
| 首页楼层(按栏目取数) | **是**(随栏目页逻辑) | `src/server/layout/index.ts:123` 复用 `listPublishedByCategory` |
| 商品列表(product 栏目) | **是**(同一函数) | product 分支走同一 orderBy |
| 站内搜索 `/search` | 否 | `searchPublished`(index.ts:828):此刻用户要的是相关性,不该被运营位干扰 |
| llms.txt / sitemap | 否 | 机器可读索引,顺序无意义且不该被人为干预 |
| 后台内容列表 | 否(仅显示标记) | 后台按 id 倒序,方便找新内容 |

**置顶只作用于「已发布」内容**——草稿/下架/定时未到点的内容本来就进不了前台列表,标记保留但不生效(与 V4.8.0 拟真数据的 PUBLISHED 闸门同一思路)。

## 3. 数据模型

```prisma
model Content {
  // …既有字段不动…
  pinnedAt     DateTime? // 置顶时刻:非空=已置顶(排序依据,越近置顶的越靠前)
  pinExpiresAt DateTime? // 置顶到期时刻:null=永久;到点自动失效(懒清理,见 §5)
}
```

只加两列、可空、默认 NULL → **存量数据零变化,升级后前台顺序与现在完全一致**。
不建新表(置顶是内容自身的属性,一对多关系没必要)。

## 4. 排序实现(无需原生 SQL)

把两处 orderBy 从 `[{ publishAt: "desc" }, { id: "desc" }]` 改为:

```ts
[{ pinnedAt: "desc" }, { publishAt: "desc" }, { id: "desc" }]
```

**为什么这样就能"置顶在前"**:SQLite 把 NULL 视为最小值,`DESC` 排序时 NULL 自动落在末尾。
本机实测(`data/app.db`,18 条 publishAt 为 NULL 的记录):

```
DESC 末尾 5 行 → 全是 NULL;publishAt ASC 头 3 行 → 全是 NULL
```

所以 `pinnedAt desc` = 已置顶(非 NULL)在前、按置顶时间倒序,未置顶(全 NULL)按原有时间倒序 **原封不动**。无需 raw SQL、无需额外字段参与排序。

## 5. 到期自动失效(懒清理,不引入定时任务)

本项目没有 cron,沿用既有 `promoteScheduled()`(定时发布到点晋升)的同款做法:
在列表读取前置一次批量清理 ——

```ts
// 过期的置顶一次性摘掉(只影响命中行,通常在 0 行,代价可忽略)
updateMany({ where: { pinnedAt: { not: null }, pinExpiresAt: { lte: now } },
             data: { pinnedAt: null, pinExpiresAt: null } })
```

好处:排序 SQL 保持简单;停机再久也不会出现"早该到期的置顶还挂着"。

## 6. 后台交互(三处,复用既有设施)

1. **内容列表行内**:标题旁显示 📌 状态 + 行尾加一个「置顶/取消置顶」图标按钮(即时生效,不弹窗、不刷新整页);
2. **批量操作**:批量栏加「批量置顶 / 取消置顶」——复用既有批量端点,只需在
   `src/app/api/admin/contents/batch/route.ts:15` 的 `z.enum(["publish","offline","draft","delete"])` 里加两个动作(逐项回执机制现成);
3. **内容编辑页**:「置顶」开关 + 可选「到期时间」(留空=永久)+ 说明文字(与 V4.8.0 拟真卡片同区域排布)。

所有置顶操作写 `logAdmin`(action=`content.pin` / `content.batch.pin`),可在操作日志里追溯谁顶的、什么时候顶的。

**数量提示**:列表顶部显示「当前置顶 N 篇」;`N ≥ 4` 时提示"首页最新动态(共 6 条)将被置顶占满"。

## 7. 前台展示

- 卡片(栏目页/首页/楼层)在标题前显示「置顶」小徽标(品牌色描边 chip),避免访客以为排序坏了;
- 文案走 i18n:zh-CN「置顶」/ en `Pinned`;沿用 `viewsLabel` 的传参模式(卡片由调用方传 label,不在组件里硬编码文案);
- 详情页不加置顶标记(单页无排序语义)。

## 8. 边界与风险

| 项 | 处理 |
|---|---|
| 置顶内容被删除 | 标记随行消失,无残留 |
| 置顶内容转草稿/下架 | 前台不再出现(本就如此);重新发布后置顶仍有效 |
| 多条置顶占满首页(6 条位) | 后台数量提示;不做硬限制(见待确认 E) |
| 与「价格排序」的语义冲突 | 默认:显式点价格排序时不置顶优先(见待确认 B) |
| 分页 | 置顶项固定出现在第 1 页(自然结果),不会重复计页 |
| 换数据库 | 依赖 SQLite 的 NULL 排序语义;若将来换 PostgreSQL,`DESC` 默认 NULLS FIRST,需补 `nulls: "last"`(已在代码注释里标注) |
| 与 V4.8.0 拟真数据 | 无耦合:置顶只影响顺序,不吃任何计数 |

## 9. 测试与验收(新增 10 条量级)

1. 栏目页列表:置顶项排第一;取消置顶后回到时间序;
2. 首页最新动态:同上(`take=6` 场景);
3. 多条置顶:按置顶时间倒序;
4. 到期自动失效:过期置顶不再排前,且库里字段被清空(懒清理生效);
5. 未到期不误清;
6. 草稿置顶不生效(不进前台列表);
7. 分页第一页含置顶、第二页不重复出现;
8. 批量置顶/取消置顶接口(逐项回执 + 上限 100);
9. 卡片渲染出「置顶」徽标(锁 select→shapeCard→组件 整链);
10. 后台列表/编辑页字段往返(zod 不剥离:UI → payload → zod → 服务层 → 回读,五处同步铁律)。

验收方式:本地演示 —— 置顶一篇 30 天前的老文,看它是否出现在栏目页与首页首位、取消后回原状、设 1 分钟后到期看是否自动落下。

## 附:两个回归缺陷修复(2026-09-20 补丁,用户报障后核实)

### BUG-1 前台投稿富文本插图报错(401)

**现象**:前台用户投稿时,正文编辑器点「插入图片」报错。

**根因**:V4.1.1「素材选择器统一入口」改造把编辑器的 `uploader` 通道删了(只留类型声明,
类型检查发现不了未使用的 props),图/视频按钮一律拉起**管理员专属**的素材库选择器;
投稿表单传入的 `uploader={userUpload}` 从此被静默忽略。

**证据**:
- 接口实测(纯前台用户 cookie):`GET /api/admin/media?picker=1` → **401**;`POST /api/admin/upload` → **401**;
  本该走的 `POST /api/upload?purpose=submission` → 400(说明鉴权通过,只是没人调它)
- 代码:`rich-text-editor.tsx` 中 `uploader` 仅出现在类型声明;`submit-form.tsx:123` 传入即被忽略
- git 追溯:基线 `bfc4dee` 有 `const doUpload = uploader ?? apiUpload(file)`;`cf058ae`(V4.1.1)删除 `doUpload`
  与两个隐藏 file input;`cbaccb8`(V4.2)由 MediaPicker 接管按钮

**修复**:编辑器保留双通道 —— 传了 `uploader` 走**本地文件选择 + 该通道**(前台投稿),
未传时维持素材库(管理员)。投稿通道限制 `png/jpeg/webp/gif`,失败给中文提示。

**验证**:浏览器端到端实测(用真实登录的前台用户):点插图 → **素材库未打开**、网络只出现
`POST /api/upload → 200`、正文插入 `<img src="/uploads/2026/09/….webp">`、提示「图片已插入」;
素材库计数 +1 且 `uploaderType=user`。截图见 `gui-test-screenshots/v481-bug-核实/`。

### BUG-2 子账号登录弹红条「无权限执行此操作」

**现象**:子账号登录后台,立刻弹红色错误提示,但功能不受影响。

**根因**:登录成功后**硬编码跳 `/admin/dashboard`**,而该页是主账号专属(`requireOwner`);
子账号必然拿到 403,页面 `catch` 直接 `toast.error(e.message)` 弹红条。
侧边栏其实已正确隐藏「数据看板」(`canSeeMenu` 把 `/admin/dashboard` 列在 OWNER_ONLY_MENUS),
所以只有登录瞬间那一下。

**证据**:`GET /api/admin/dashboard`(仅 content 权限的子账号)→ **403 无权限执行此操作**;
同账号 `GET /api/admin/contents` → **200**。

**修复**:
1. 新增纯函数 `resolveAdminLanding(role, permissions)`:OWNER → 看板;STAFF → 第一个有权限的菜单;
   一个权限都没有 → 返回 null;
2. `/admin` 入口页按上述结果跳转(一个权限都没有时渲染「尚未分配后台权限」空态);
   登录成功改为跳 `/admin`;
3. `api-client` 的错误对象携带 HTTP 状态 + 新增 `isForbiddenError`;看板页遇到 403 渲染
   页面内空态,不再弹红条(防止有人直接输 URL 进来看到红字)。

**验证**:子账号(`content` 权限)登录实测 → 落地页 `/zh-CN/admin/content`,提示只有
「登录成功」,侧边栏只显示已授权菜单。截图同上目录。
