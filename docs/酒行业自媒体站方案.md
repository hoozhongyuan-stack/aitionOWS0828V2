## 2. 站点骨架（建议）

### 2.1 一级导航（5 项，去掉产品化的"定价/产品/解决方案矩阵"）

```
首页 | 酒业洞察 | 解决方案 | 案例 | 关于我
```

- 旧导航 20 项（产品 / 产品中心 / 商品演示 / 定价 / GEO 学院 …）**整体废弃**，那是"卖系统"的结构。
- 「酒业洞察」下拉出 5 个二级；「解决方案」下拉出 7 个二级（6 类系统 + 合作方式）；「案例」「关于我」直达。
- **观点台账**与**订阅**不进主导航（避免导航臃肿），挂在首页与页脚——它们是资产型页面，不是日常阅读入口。

关于我    about            （page）   固定单页

**四个关键取舍（都有理由）**

1. **主结构按"内容类型"而不是按"受众"分。**《项目指令》要求每篇只面向一类受众，但受众是横切的二维（同一主题里酒企和经销商都关心），而平台**没有标签/受众字段**，用栏目表达受众会把主题轴压平。所以做法是三层配合：① 每个二级栏目天然有一个**主受众**（见上表右列）② 每篇文章首段明示受众（你写作时本来就会做）③ 首页用**两个楼层**把受众分开（渠道与终端＝经销商向、消费者与会员＝酒企向），读者从标题就能对上号。**要彻底做受众筛选，需要小开发加字段**（见 §6）。
2. **11 个监测方向合并成 5 个二级栏目。** 11 个方向里有一半是同一批读者关心的相邻话题（③④⑧ 都是渠道侧，①⑦ 都是消费者侧），拆成 11 个栏目会让每栏只有一两篇、页面显得空。**特别地：第 ⑪ 项"同行内容监测"不对外设栏目**——它是你内部的查重流程，是方法而不是内容。
3. **不设"产品"一级栏目，也不要用 `product` 模块类型。** 平台的栏目类型里只有 `product` 有特殊渲染（商品卡 + 价格 + 加购 + 下单），你写的是能力说明不是 SKU，一旦用成 product 就会出现价格/购物车按钮，与"不生硬广告"的原则冲突。全部用 `article` / `page`，图文呈现。
4. **站点对外只用通用产品名。** 《项目指令》§五.1 要求公开内容不出现软件公司名称/品牌/域名/标识——落到站点上就是：栏目名、页面标题、正文一律用"消费者运营管理系统"这类通用名，站点自身品牌（爱神AiTion）与软件供应方在内容里不混为一谈。

### 2.3 首页编排（沿用现有 `spotlight` 全幅聚焦）

1. **首屏**：一句话定位 + 一句可信背书 + 「聊聊你的项目」CTA（双按钮）
2. **受众分区**：不追求"两张入口卡"（那需要开发），**零开发的等效做法是用两个楼层把受众分开**——「渠道与终端」（经销商向）与「消费者与会员」（酒企向）各占一个楼层，读者从标题就能对上号。真要两张卡，见 §6 小开发 H。
3. **最新洞察**：最新 5 篇（SSR 列表，最新优先）
4. **主题楼层**：只挑 2 个当下最有量的栏目（如「渠道与终端」`feature` 1 大 + 2 小、「消费者与会员」`feature`）——**栏目开齐便于归类，但首页只展示有量的**，避免冷启动时页面显得空
5. **解决方案入口**：6 类系统的入口（零开发可用一个楼层承载，或首屏第二个 CTA 指向 `/c/solutions`）
6. **案例**：1–2 篇（起步阶段可先不放，等有授权案例）
7. **订阅 / 联系 CTA**

> ⚠️ 现有 `floors` 配置还指向已被删除的栏目 id 15 / 11（悬空），重建首页时必须重设。

### 2.4 固定页与资产页

- **关于我**：酒行业从业经历 + 亲手实施过的系统 + 服务方式（B 端信任的关键，写实、写细）
- **联系**：表单（需重建）+ 微信二维码 + 电话
- **观点台账**（差异化资产）：对外展示"我们说过什么、什么时候说的、依据是什么、后来验证没有"。这是《项目指令》§十三观点库的对外切片——同类自媒体没人敢公开自己的历史判断，这恰恰是最难被抄的信任资产。**第一版零开发**：用一篇单页人工维护表格；等条目多了再考虑结构化页面（§6）。
- **订阅**：RSS + 邮件（见 §6 小开发）；零开发的过渡方案是用「表单」收集订阅意向（提交记录即名单）
- **法律三件套**：注册协议 / 隐私政策 / Cookie 政策（已存在，注意文字仍偏"软件产品"口径，需改成顾问服务口径）

## 4. 解决方案栏目：7 个二级页怎么建

对应 §2.2 的 `solutions` 子树。**6 个系统栏目页共用同一套结构模板**，写完一个可套用其余五个。

**4.1 系统栏目页的固定结构（模板）**

| 段落 | 写什么 |
| --- | --- |
| 顶部（栏目描述自动渲染在标题下） | 一句话：这个系统解决什么问题、适合谁 —— **就是栏目描述那句，不用另写能力说明文章** |
| 一、问题 | 谁的什么指标不对（写具体的人和物，不写"影响经营"） |
| 二、机制 | 为什么会这样 —— 这是你区别于同行的部分（B 类"更深入"内容的落点） |
| 三、能力 | 系统怎么解，做到什么、做不到什么（边界写清反而提升信任） |
| 四、场景与适配 | 对应《项目指令》§九 的匹配关系（什么场景该用这套），直接搬那张表 |
| 五、项目经验 | 已公开的案例或经验（无则留白，不编） |

**4.2 六类系统的定位分工（避免互相抢话题）**

| 系统栏目 | 解决的问题域 | 典型话题归属 |
| --- | --- | --- |
| 即时零售 `instant-retail` | 线上生意、履约与门店在线化（含私域与会员复购） | 同城配送、前置仓、多门店、会员沉睡 |
| 扫码营销 `scan-marketing` | 渠道管控与动销留痕 | 一物一码成本、防窜货、渠道返利、价格秩序 |
| 定制酒 `custom-liquor` | 企业团购与个性定制 | 企业礼赠、婚宴纪念、包装定制、生产协同 |
| 封坛酒 `sealed-cask` | 高价值客户资产 | 封坛认购、藏酒、取酒转赠、老客经营 |
| 回厂游 `distillery-tour` | 体验与关系经营 | 参观品鉴、接待、研学、客户旅程 |
| 宴席酒 `banquet-liquor` | 场景化销售 | 婚宴寿宴升学宴政策、用酒台账、终端激励 |

**4.3 服务与合作方式（`engagement`）**

| 服务 | 交付物 | 适合谁 |
