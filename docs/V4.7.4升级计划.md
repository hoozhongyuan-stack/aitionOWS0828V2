# AitionOWS V4.7.4 升级计划(文章版权声明 + 评论两层回复 + 上传图片自动压缩)

> 分支 main(基于 v4.7.3) · **一次增量迁移**(Comment 加两列,可空/带默认,存量零影响) · 预计 2 天 · **2026-09-16 用户确认 5 项推荐后已实施(见文末)**
> 范围:① 文章底部版权/转载声明(可转载、须注明来源与网址) ② 评论回复(后台回复 + 两层嵌套) ③ 上传图片自动压缩(回应 3M 带宽下图片加载慢)
> 说明:本文档只做分析与方案,确认后再动代码

## 一、问题确认(证据)

### 1. 文章无版权声明

文章底部顺序:关键词标签 → 收藏/点赞/转发 → 评论区,无任何版权/转载说明;文章 JSON-LD 也只有作者、没有许可信息。访客与转载者拿不到"可以转载、怎么标注"的指引。

### 2. 评论**:后台其实还没有"回复"功能**(对上轮结论的诚实修正)

核实代码与生产数据后的**更正**:后台评论操作只有 通过/驳回/删除 三个,**并没有"回复"按钮**;`Comment` 表也**没有 `parentId` 字段** —— 所有评论是同一级扁平列表,不存在"回复后再回复"的结构(生产库现有 2 条评论、0 条回复)。用户感知的"可以回复但回复后不可再回复",实际是"只能另发一条独立评论"。因此本项要做的是**从零建立回复能力 + 两层嵌套结构**。

### 3. 图片慢:瓶颈是体积不是带宽本身(实测)

那篇文章(3M 带宽 ≈ 375 KB/s):

| 图 | 原始 | 3M 带宽耗时 |
|---|---|---|
| 封面 1200×675 **PNG** | 1.72 MB | ~4.6s |
| 正文图 1920×1080 **PNG** | 2.42 MB | ~6.4s |
| 其余 4 图 | ~0.13 MB | ~0.4s |
| **合计** | **4.3 MB** | **~11.5s 起步** |

全站盘点:最大封面 **2.9MB**(1672×941 PNG),6 篇文章封面全部是 1.3–1.9MB 的 PNG —— **AI 生成的海报类图片原样直出**,上传链路没有压缩环节(sharp 在容器里但未使用)。懒加载已有(正文图带 `loading="lazy"`),救不了首屏与图片本身的大小。

**压缩可行性实测**(用线上原图 + 项目自带的 sharp,按方案参数 WebP q82 / 分享 JPG q85):

| 图 | 原始 PNG | 显示 WebP(q82) | 分享 JPG(q85, 1200w) |
|---|---|---|---|
| 封面 1200×675 | 1,722 KB | **108 KB(15.9 倍)**,分辨率不变 | 147 KB |
| 正文 1920×1080 | 2,418 KB | **127 KB(19 倍)**,缩至 1600×900 | 125 KB |

对比样本已存 `gui-test-screenshots/v474-图片压缩对比/`(原图与压缩图并排),可亲眼比对清晰度。

## 二、修改方案

### A. 文章版权/转载声明(0.25 天)

1. **声明块**:文章页**关键词行之下、互动条之上**(即用户截图红框位置)渲染:
   > 本文由 数字中圆 原创,欢迎转载 —— 转载请保留出处与链接:
   > `https://www.aition.xin/zh-CN/article/<slug>`
   - 站名取品牌配置;**网址以纯文本呈现**(不做超链接)—— 转载者复制正文时链接才会被带走
2. **复制带来源**:监听正文容器的 copy 事件,剪贴板自动追加一行「来源:数字中圆 · 原文链接:<URL>」—— 公众号同款机制;只追加、不改写用户复制的内容
3. **JSON-LD**:`Article` 增加 `license`(取 Creative Commons BY-NC 4.0 链接,常量;是否允许商用转载见待确认项)
4. i18n:`article` 命名空间新增键(中英同步)

### B. 评论两层回复(0.5 天,含迁移)

1. **迁移(增量、可空)**:`Comment` 加 `parentId Int?`(回复指向被回复的评论)+ `isAuthorReply Boolean @default(false)`(作者回复标记);`migrate deploy` 由容器启动脚本自动执行
2. **后台**:评论行新增「回复」操作(promptDialog 输入内容)→ 创建 `status=APPROVED, parentId=原评论, isAuthorReply=true` 的评论,显示名用品牌站点名(如「数字中圆」);AdminLog 记 `comment.reply`
3. **前台**:两层渲染 —— 回复缩进挂在原评论下,带「作者」徽标;**回复的回复**(如有)也归拢到同一顶层评论下并 `@目标`(保持最多两层视觉,避免楼中楼失控)
4. **边界**:访客发评论入口不变(只能顶层);原"通过/驳回/删除"对回复同样适用;删除父评论时级联删除其下回复(应用层处理,`parentId` 不设外键级联,避免误删放大)
5. 测试:回复创建链路、两层取数(父→子排序)、删除父连带子、前台渲染断言

### C. 上传图片自动压缩(1 天,含存量回填)

**压缩规则**(上传时执行,管理端/前台投稿共用入口):

| 项 | 规则 |
|---|---|
| 处理范围 | mime 为 jpeg / png / webp 的图片;GIF(动图)/SVG/ICO 跳过 |
| 显示版本 | WebP q82,宽 ≤1600 只缩不放 |
| 分享伴生版 | JPG q85,宽 ≤1200 —— 专供 og:image(**微信分享卡不吃 WebP**,V4.7.1 已踩过) |
| 兜底 | 压缩结果比原图**更大**时保留原图不替换;**原文件保留在磁盘不删除**(回滚安全) |
| 登记 | WebP 为主资产(新 UUID 路径),JPG 伴生也登记 MediaAsset(宽高同),`width/height` 照常记录 |

1. **og:image 集成**:`pickShareImage` 对每个候选优先寻找其 JPG 伴生资产(有则用,无则按现规则走)—— 分享卡体积也从 1.7MB 级降到 ~150KB
2. **存量回填(一期只做封面)**:`scripts/backfill-image-variants.mjs` 遍历已发布文章的 `coverUrl`,逐张生成 WebP + JPG 伴生并更新 `Content.coverUrl`;**正文图一期不动**(懒加载已兜底,且批量改正文 HTML 风险高,需要时二期再做)
3. 测试:压缩函数(格式分支/尺寸上限/变大保留)、上传集成断言(WebP 落库 + JPG 伴生登记)、og builder 优先伴生、封面回填脚本 dry-run

**回答"压缩后还清晰吗"**:清晰。① **分辨率不降**——1200×675 的封面压完还是 1200×675,只有超过 1600px 的才等比缩到 1600(前台最大展示宽约 1080px,1600 已覆盖 2x 视网膜屏);② 压的是**编码冗余**不是像素 —— WebP q82 在海报/照片类图像上与 PNG 肉眼不可分(15–19 倍的体积差主要来自 PNG 对这类图像的编码极低效);③ 对比样本已放在 `gui-test-screenshots/v474-图片压缩对比/`,请亲眼比对后再定;④ 兜底规则保证"压了反而更大"的图不会被压。若你看过样本后仍想要更高画质,参数可上调为 q88–q92(体积约 +30–60%,仍远小于 PNG)。

## 六、实施结果(2026-09-16,用户确认 5 项推荐后执行)

**用户裁定**:q82 / 只回填封面 / CC BY-NC 4.0 / 只做后台回复 / 回复显示名「数字中圆」。

| 项 | 实施 | 实测 |
|---|---|---|
| A 版权声明 | 关键词下声明块(站点名取品牌配置 + **纯文本** URL);`CopyAttribution` 客户端组件包正文(onCopy 追加来源行);ArticleJsonLd `license` = CC BY-NC 4.0;i18n `article.copyrightNotice` | SSR 含声明文案 + `/zh-CN/article/<slug>` 纯文本 URL;JSON-LD license 存在 |
| B 评论回复 | 迁移 `20260916122125_comment_threading`(parentId + isAuthorReply + FK 级联 + 索引);`replyAsAuthor`(站点名/直发 APPROVED/目标为回复时归拢同顶层);路由 `action:"reply"`;后台弹窗回复;前台两层渲染 + 「作者」徽标(i18n `interaction.authorBadge`);删除父连带删回复 | 后台回复后前台 API 返回两层结构;对回复再回复 parentId 归拢到顶层;删除连带验证通过 |
| C 上传压缩 | 压缩逻辑抽为 `src/lib/storage/variants.ts`(单一来源可单测);saveUpload 接入;**mime/扩展名随显示版变 webp**;createMedia 登记 JPG 伴生;og `pickShareImage` 优先伴生(两种命名);回填脚本 dry-run/--apply | 1.7MB 海报 → **108KB WebP + JPG 伴生**;207KB 小图触发"无收益保留原图";回填 197KB→105KB、og 自动取 `-share.jpg` |

**开发中发现并修掉的三个自伤缺陷**(均已写入 CHANGELOG 修复段):
1. 转 WebP 后主资产仍登记 .png/mime=image/png(内容与扩展名不符)→ mime 随显示版
2. 回填伴生 `stem.jpg` 与原 .jpg 资产**同路径撞车** → 改名 `-share.jpg`,og 推导兼容两种命名
3. 同 path 重复行把 getMediaDimensions 的 Map 覆盖(空 dims 盖合格行)→ 取数优先非空行

**一次操作失误(如实记录)**:本地调试回填时,`rm` 清理伴生文件误删了两张**本地测试文章的原封面**(path 恰为 `stem.jpg`);生产无此二文件(生产从未有这两条记录,不受影响),已用同尺寸占位图写回原 path 恢复 URL(占位图上明确标注"本地测试封面占位图")。教训:按模式批量删文件前必须逐个核对是否为原资产。

门禁:293 测试全绿(新增 15 条)、lint 0 warning、tsc 清零、next build 通过。

**生产发布注意**:① 部署时 entrypoint 自动 `migrate deploy` 执行评论迁移;② 上线后可跑一次回填脚本(服务器无 node 直跑条件 → 建议本地连生产库副本验证后,在生产容器内 `docker exec` 执行,或等下次发版把脚本带上);③ 存量正文大图属二期。
